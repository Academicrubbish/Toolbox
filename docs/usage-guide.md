# Toolbox 项目 — AI 协作开发使用说明

## 一句话说明

告诉 Claude 你的需求，它会按 **Spec → Design → Plan → Execute** 的流程逐步推进，每步产出可 review 的文档，你确认后再进入下一步。

---

## 第一步：判断场景

拿到需求后，先判断走哪个场景：

```
拿到需求
├─ 全新功能？          → 场景一：新需求开发（完整流程）
├─ 改已有功能？        → 场景二：需求变更（从受影响文档回补）
├─ Bug / 线上问题？    → 场景三：Bug 修复（轻流程 or 回补文档）
├─ 技术债 / 重构？     → 场景四：重构（按影响深度选文档）
└─ 改文案/配置/小参数？ → 场景五：低风险小改动（commit 留痕即可）
```

**判断原则：** 先看场景，不看代码量。不确定就多补一层文档。

---

## 场景一：新需求开发（最常用）

假设你要新增一个「学习数据统计」功能，完整流程如下：

### 1. 生成 Spec（需求文档）

**你这样说：**

```
帮我用 taiji-spec 新增一个需求：学习数据统计功能。
用户可以在首页查看本周/本月的学习记录数、AI笔记生成数、
学习天数等统计数据，以卡片形式展示在首页顶部。
```

**Claude 会做什么：**
- 分析需求，判断是否需要拆分（功能点 >5 / 表变更 >3 等信号）
- 选择合适的格式（功能列表 / 用户故事 / 用例）
- 在 `docs/learning-stats/spec.md` 生成需求文档
- 包含：背景、目标、功能描述、验收标准、边界条件

**你需要做的：** Review spec 内容，确认需求描述和验收标准没问题。

### 2. 生成 Design（设计文档）

Spec 确认后：

```
spec 确认了，继续用 taiji-design 生成设计文档。
```

**Claude 会做什么：**
- 先读取 `docs/codemap.md`（了解项目现有能力）
- 读取 spec 文档
- 判断需要哪些章节（时序图、数据结构、边界情况等）
- 在 `docs/learning-stats/design.md` 生成设计文档
- 包含：模块划分、核心流程、接口设计、数据结构等

**你需要做的：** Review 设计方案，确认技术选型和接口设计。

### 3. 生成 Plan + Tasks（实施计划）

Design 确认后：

```
design 确认了，继续用 taiji-plan。
```

**Claude 会做什么：**
- 分析设计文档的模块依赖关系
- 划分实施阶段（先做被依赖的模块）
- 生成 `docs/learning-stats/plan.md`（实施计划）
- 生成 `docs/learning-stats/tasks.md`（具体任务清单）
- 每个任务包含：操作类型、涉及文件、实现细节、测试用例

**你需要做的：** Review 计划，确认实施顺序和任务拆分合理。

### 4. 执行编码

Tasks 确认后：

```
tasks 确认了，用 taiji-execute 开始编码。
```

**Claude 会做什么：**
- 逐个任务执行：读代码 → 写功能代码 → 写测试 → 运行测试
- 每完成一个任务向你汇报进度
- 失败自动重试（最多 3 次）
- 全部完成后生成 `docs/learning-stats/code-report.md`

**你需要做的：** 监控进度，处理需要人工决策的问题。

### 5. Code Review + 提交

编码完成后：
- Review 代码变更（`git diff`）
- 确认 code-report 中的验收覆盖
- 提交代码

## 场景二：需求变更

假设「学习数据统计」做到一半，产品说要加一个「导出统计报表」功能：

```
需求变更：学习数据统计需要新增导出报表功能，
支持导出 PDF 格式的周报和月报。
请按场景二处理，从受影响文档开始回补。
```

**Claude 会做什么：**
1. 分析变更影响范围（影响验收标准 → 从 Spec 回补）
2. 修改 `spec.md`（新增导出验收标准）
3. 修改 `design.md`（新增导出方案设计）
4. 修改 `plan.md` + `tasks.md`（调整实施计划）
5. 继续执行更新后的 tasks

**核心原则：先改文档再改代码，不要反过来。**

## 场景三：Bug 修复

### 轻流程（原因明确、影响面小）

```
修复一个 bug：首页列表在游客状态下不显示示例数据。
这是一个显示问题，原因明确，走轻流程。
```

直接修复 → 验证 → commit（commit message 写清楚改了什么、为什么、怎么验证）。

### 回补文档（设计缺陷、跨模块问题）

```
修复一个 bug：AI 笔记生成后，切换用户登录状态，
显示的是上一个用户的结果。这是一个状态管理的设计缺陷。
```

**Claude 会做什么：**
1. 分析 bug 暴露的是哪一层问题（设计假设错误）
2. 回补受影响的 design 文档
3. 修复代码
4. 更新 code-report

## 场景四：重构

```
重构：将首页的记录列表、搜索、标签管理拆分为独立模块，
提升代码可维护性。涉及 3 个以上模块边界调整。
```

**Claude 会做什么：**
1. 定义不变的外部行为（用户看到的交互不变）
2. 生成 spec（目标 + 边界）
3. 生成 design（模块拆分方案）
4. 生成 plan + tasks
5. 执行重构
6. 验证外部行为未变

---

## 场景五：低风险小改动

```
把首页标题从 "markdown" 改为 "Markdown 笔记"。
```

直接改 → 验证 → commit。不需要写文档。

## 常用指令速查

| 你想做什么 | 怎么说 |
|-----------|--------|
| 新建需求 | `用 taiji-spec 生成需求文档：[描述需求]` |
| 修改需求 | `需求变更：[描述变更]，按场景二处理` |
| 生成设计 | `spec 确认了，用 taiji-design 生成设计` |
| 生成计划 | `design 确认了，用 taiji-plan 生成计划` |
| 开始编码 | `tasks 确认了，用 taiji-execute 开始执行` |
| 更新 codemap | `用 taiji-codemap 更新代码地图` |
| 只修 bug | `修复 bug：[描述问题]，走轻流程` |
| 快速跳过确认 | 在指令末尾加 `quick mode` |

## 文档产出位置

每个功能在 `docs/` 下有自己的目录：

```
docs/
├── codemap.md                    # 项目代码地图（全局唯一）
├── spec-standard.md              # Spec 书写规范
├── usage-guide.md                # 本使用说明
└── learning-stats/               # 功能目录（kebab-case 命名）
    ├── spec.md                   # 需求文档
    ├── design.md                 # 设计文档
    ├── plan.md                   # 实施计划
    ├── tasks.md                  # 任务清单
    └── code-report.md            # 执行报告
```

---

## 关键提醒

1. **每一步都要你确认后再往下走** — 不要跳过 review
2. **先读 codemap 再写代码** — Claude 在 Design/Plan/Execute 前会自动读取
3. **文档是 AI 的输入** — spec 写得越清楚，生成的代码质量越高
4. **可重放是最大价值** — 代码不满意？基于文档重新生成就行
5. **不确定就多补一层文档** — 宁可多写不要少写
