# 第 1 章 引言

## 1.1 编写目的

本文档是 Toolbox 小程序从"笔记工具"向"个人知识库"升级的完整开发方案，按软件开发生命周期（SDLC）组织，覆盖：现状分析、需求分析、总体设计、分期实施计划、测试计划、风险管理、成本与部署。

每一期功能均给出：目标、任务分解、涉及文件、测试方法、验收标准。文档既是开发蓝图，也是每期上线前的验收依据。

## 1.2 项目背景

### 1.2.1 项目初心与演进

Toolbox 最初的定位是"手机上能看 Markdown 文档的小程序"，解决个人学习资料移动端阅读的问题。经过迭代，目前已具备：学习记录管理、Markdown 编辑渲染、标签体系、AI 辅导笔记与练习题生成、文章分享等功能。

进入 AI 时代后，笔记类工具正在整体向"个人知识库"方向演进。核心判断是：**大模型 + 个人积累的笔记 = 强大的个人知识资产**。笔记工具解决"记下来"，知识库解决"找回来、连起来、问出来"——而后三件事恰恰是人脑最不擅长、工具最有价值的部分。

### 1.2.2 什么是个人知识库（通俗说明）

用一个比喻：现在的 Toolbox 是一本**流水账**——每笔账都记了，但要查"去年我在学习上花过哪些功夫"，只能一页页翻。知识库就是给账本请了一位**账房先生**：

1. 他把每笔账都"读懂"了——心里给每笔账画了张位置图，意思相近的账挨着放（技术上是给每篇笔记算一个"向量"）；
2. 你随口问，他能找到——你说"上个月那笔买书的钱"，哪怕账上写的是"购书支出"，他也知道是一回事（语义搜索）；
3. 他还能替你盘账——"您这笔账，跟去年九月那笔是一类事，要不要放一起看看？"（相关笔记、复习提醒）。

对应到本方案的四类核心功能：

| 用户痛点 | 知识库的做法 | 功能名称 |
|----------|-------------|---------|
| 记过但找不到；换个说法就搜不到 | 按"意思"找，不按字面找 | 语义搜索 |
| 想直接问问题，不想翻笔记 | 检索相关笔记，由 AI 汇总成答案，并注明"根据哪几篇" | 知识库问答（RAG） |
| 新旧知识各记各的，互相不认识 | 自动发现笔记之间的关联 | 相关笔记推荐 |
| 老笔记沉底，不知道该复习什么 | 按遗忘节奏主动提醒 | 间隔复习 |

### 1.2.3 方案边界（知识库不解决什么）

知识库**不替用户理解知识**。它负责"存得住、找得回、连得起"，而"学进去"由现有的 AI 辅导笔记与练习题功能承担。两者是互补关系：

- AI 辅导 → 管"学进去"（讲解、出题）
- 知识库 → 管"存得住、找得回"（检索、问答、关联、复习）

## 1.3 项目目标与成功标准

**总目标**：在不动现有数据库结构与核心功能的前提下，通过分六期迭代，将 Toolbox 升级为具备语义搜索与知识库问答能力的个人知识库。

**成功标准**（量化验收，详见第 5、6 章）：

1. 语义搜索：同义词测试集（10 组"同义不同词"查询）通过率 ≥ 7/10；精确词（函数名、人名）命中率 10/10；
2. 知识库问答：忠实度人工评审 ≥ 8/10；拒答测试（知识库中无答案的问题）5/5 零编造；答案 100% 带可点击引用；
3. 全程"只做加法"：任何一期可独立回滚，回滚不损伤任何现有数据；
4. 新增月度成本控制在个位数人民币级别。

## 1.4 文档范围

**包含**：知识库核心功能（向量化基建、语义搜索、相关笔记、RAG 问答、自动标签、间隔复习）以及远期功能（双链、图谱）的规划。

**不包含**（另行文档管理）：

- UI 全站重构（见 `docs/ui-redesign/`）
- 学习专区多来源采集（见 `docs/learn-zone/spec.md`）——但两者在"输入管道"上有协同，见 2.5 节
- 多用户/商业化相关设计（当前按个人使用规模设计）

## 1.5 术语与名词解释

| 术语 | 解释 |
|------|------|
| 向量 / 嵌入（Embedding） | 把一段文字转换成一串数字（如 512 个数字构成的坐标）。**意思相近的文字，坐标就相近**。这是语义搜索的数学基础 |
| 向量维度 | 这串数字的个数。维度越高语义表达越细，但存储和计算量越大。本项目选用 512 维 |
| 语义搜索 | 按"意思相近程度"搜索，而不是按字面是否包含关键词 |
| 关键词（字面）搜索 | 现有 `searchRecord` 的方式：正则匹配字面文字 |
| 余弦相似度 | 衡量两个向量方向是否接近的数学方法，取值 -1 ~ 1，越接近 1 表示两段文字意思越相近 |
| 切片（Chunking） | 把长笔记切成若干段，每段单独向量化。搜索与问答以"段"为单位命中 |
| RAG（检索增强生成） | Retrieval-Augmented Generation。先检索出与问题相关的内容，再让大模型**只根据这些内容**回答，从而让回答基于个人笔记而非模型自由发挥 |
| 引用 | AI 回答中标注 [1][2] 等编号，指明该结论出自哪篇笔记，可点击跳转 |
| 幻觉 | 大模型编造不存在信息的现象。RAG + 引用机制是本方案的主要对抗手段 |
| 回填（Backfill） | 对已存在的历史笔记补做向量化的一次性操作 |
| 降级 | AI 相关功能失败时，自动退回传统可用路径（如语义搜索失败退回关键词搜索），保证不白屏 |
| 幂等 | 同一操作重复执行，结果不变。例：笔记编辑多次，向量始终只有一套，不重复堆积 |
| 任务队列 | 异步处理模式：先记录任务立即返回，后台定时消费处理。项目已有成熟先例（`ai_task_queue`） |
| 定时触发器 | uniCloud 按固定周期自动执行云函数的机制 |
| openid | 微信用户唯一标识，项目中用作数据归属（`create_by`）的依据 |

# 第 2 章 现状分析

## 2.1 系统架构现状

- **前端**：uni-app（Vue 2）编译为微信小程序；主包 + 分包结构；towxml 渲染 Markdown；ColorUI / 自有组件体系。
- **后端**：uniCloud 阿里云版——云函数、云数据库（文档型）、云存储、定时触发器、JQL。
- **第三方服务**：
  - 智谱开放平台 GLM-5（AI 辅导笔记生成、公众号文章清洗），OpenAI 兼容接口，`ZHIPU_API_KEY` 按云函数隔离配置；
  - 阿里云百炼 qwen3.6-flash（OCR 图片识别，规划中）。
- **异步处理**：`generateLearnNote` 写任务队列立即返回 → 定时触发器驱动 `processLearnNote` 消费队列 → 客户端轮询取结果。该模式已稳定运行，是本方案直接复用的架构范式。
- **管理端**：`admin.html` + `getAiStats` 云函数，监控 AI 调用量与 token 消耗，配套 `checkAiAlert` 告警。

## 2.2 现有功能清单

游客/登录双模式（`withAuth` 授权体系）、学习记录 CRUD、标签管理（`dict_category` / `dict`）、Markdown 编辑与渲染（含 LaTeX / ECharts / Mermaid 云函数渲染）、AI 辅导（知识点精讲 + 练习题）、学习结果查看、文章分享、更新日志、AI 统计管理。

## 2.3 数据模型现状

| 集合 | 说明 | 关键字段 |
|------|------|---------|
| `daily_record` | 学习记录（主体） | title、summarizeId、tags、createTime、createBy |
| `summarize` | 笔记正文（Markdown） | content、recordId、category、createTime |
| `dict_category` / `dict` | 标签体系 | name、description、createBy |
| `ai_learn_logs` | AI 辅导结果 | record_id、source_content、ai_result、type（note/exercise）、batch_id、status |
| `ai_task_queue` | AI 任务队列 | content、status（pending/processing/done/failed） |
| `ai_call_logs` | AI 调用日志 | token 用量（成本监控复用） |
| `tb_user` | 用户信息 | userName、_openid |
| `changelog` / `share_links` | 更新日志 / 分享链接 | — |

**要点**：笔记的"标题"在 `daily_record`，"正文"在 `summarize`（通过 `summarizeId` / `recordId` 双向关联）。向量化时需要把两者拼接处理。

## 2.4 现有搜索的实现与问题分析

现状实现（`cloudfunctions/searchRecord`）：

1. 拉取 `summarize` **全表**（未按用户过滤）到云函数内存，正则逐条匹配内容；
2. 拉取当前用户全部 `daily_record`，正则匹配标题与时间；
3. 两路命中的记录 ID 合并去重，最后再按 `createBy` 过滤返回。

存在的问题：

| 编号 | 问题 | 影响 | 本方案的对策 |
|------|------|------|-------------|
| P1 | **只认字面**：搜"背单词的方法"找不到写着"记词窍门"的笔记 | 语义检索能力缺失，是本方案要解决的核心问题 | 语义搜索（第二期） |
| P2 | **无相关度排序**：命中即返回，按时间倒序，无法体现"哪篇最相关" | 搜索质量差 | 余弦相似度排序（第二期） |
| P3 | **全表扫描**：每次搜索把全库 `summarize` 读进云函数内存 | 数据量增长后内存与耗时线性上升，存在超限风险 | 新方案在**数据库查询层**按 openid 过滤，只读本人向量 |
| P4 | **中间过程读取全库数据**（虽然最终输出前做了归属过滤） | 不必要的数据暴露面 | 同上，查询层面收窄 |

# 第 3 章 需求分析

## 3.1 目标用户与使用场景

**目标用户**：开发者本人（个人学习者），以及未来的少量分享用户。游客模式不涉及知识库功能（知识库检索与问答均要求登录）。

**四个核心痛点场景**（需求来源）：

**场景一："我明明记过这个！"**
三个月前学某概念时记过笔记，今天要用却忘了细节。打开小程序搜索，只有当搜索词恰好出现在标题或正文里才能命中——如果当时笔记标题写的是"状态管理心得"而今天搜"reducer"，就擦肩而过。**笔记还在，只是它"沉默"了。**

**场景二：换个说法就失灵。**
搜"背单词的方法"，笔记里写的是"记词窍门"。人一看就懂是同一回事，字面匹配却无能为力。

**场景三：想直接问问题，而不是搜关键词。**
"我之前学 hooks 的时候，笔记里是怎么说的？"——这不是一个关键词，是一个**问题**。现有工具无法回答问题。

**场景四：笔记记了就沉底。**
记了两百篇，除了最新十几篇，老笔记基本等于埋了。知识不回顾等于没学，但"该复习什么"本身就需要有人提醒。

## 3.2 功能需求清单

| 编号 | 功能 | 描述 | 优先级 | 实施期 |
|------|------|------|--------|--------|
| FR-01 | 向量化基建 | 笔记保存/编辑后自动向量化；存量笔记一次性回填 | P0（隐性基础） | 第一期 |
| FR-02 | 语义搜索 | 按"意思相近"检索笔记，返回相关度排序的 top 10 | P0 | 第二期 |
| FR-03 | 混合检索 | 语义结果与现有关键词结果合并，精确词（函数名、人名）由关键词通道兜底 | P0 | 第二期 |
| FR-04 | 相关笔记推荐 | 详情页展示与当前笔记最相似的 5 篇 | P1 | 第三期 |
| FR-05 | 知识库问答 | 向笔记提问，AI 基于检索到的笔记片段作答，答案带可点击引用 | P0 | 第四期 |

## 3.3 非功能需求

| 编号 | 类别 | 要求 |
|------|------|------|
| NFR-01 | 性能 | 语义搜索 P95 < 3 秒（当前笔记量级）；问答端到端（提交到出结果）< 60 秒 |
| NFR-02 | 安全 | 向量与问答数据的查询**必须在数据库层按 openid 过滤**；任何用户不可见他人数据；改善现状中"中间过程读全库"的问题 |

| NFR-05 | 成本 | 新增月成本个位数元级别（见第 8 章测算） |
| NFR-06 | 可维护性 | 沿用现有代码风格（api/ 一集合一文件、withAuth 包装、云函数日志规范）与文档习惯 |

# 第 4 章 总体技术方案

## 4.1 方案总览

**一句话架构**：给每篇笔记算一个 512 维"语义坐标"（向量），存进 uniCloud 新集合；搜索时把搜索词也算成坐标，在云函数内存里和本人所有笔记的坐标逐一比对（余弦相似度），取最相近的若干条；问答时先把问题检索一遍，把命中的笔记片段连同问题交给 GLM-5，要求只依据片段作答并标注引用。

**新增组件清单**：

| 类型 | 新增内容 | 数量 |
|------|---------|------|
| 数据库集合 | `note_embedding`、`embed_task_queue`、`kb_answer`、`review_schedule` | 4 |
| 云函数 | `processEmbedding`、`backfillEmbedding`、`semanticSearch`、`generateKbAnswer`、`processKbAnswer` | 5 |
| 前端 | 搜索结果增强、详情页"相关笔记"区块、"问知识库"分包页面、"今日复习"入口 | 4 处 |

**数据流**：

```
【向量化】
保存/编辑笔记 ──→ embed_task_queue ──(定时)──→ processEmbedding
                                                │ 调 embedding-3 接口
                                                ▼
                                            note_embedding

【语义搜索】
小程序搜索框 ──→ semanticSearch 云函数
                    ├─ 搜索词 → embedding-3 → 查询向量
                    ├─ 按 openid 查本人全部向量 → 余弦相似度 → top 10
                    ├─ 并行执行关键词匹配（复用现有逻辑）
                    └─ 两路合并去重 → 返回（标注匹配方式）

【知识库问答】
提问 ──→ generateKbAnswer（写 kb_answer + 任务，立即返回 ID）
              │
        (定时) processKbAnswer
              ├─ 语义检索 top 5 片段
              ├─ 片段 + 问题 → GLM-5（带三条铁律的 prompt）
              └─ 答案 + 引用列表 写回 kb_answer
              │
小程序轮询 kb_answer ──→ 展示答案 + 可点击引用
```

## 4.2 关键技术决策

### 4.2.1 决策一：不引入外部向量数据库（核心决策）

**背景**：实现语义搜索的行业主流方案是专用向量数据库（Milvus/Zilliz、Qdrant、腾讯 VectorDB、阿里 DashVector）。本项目明确**不采用**，理由如下。

**理由 1：uniCloud 数据库本身没有向量索引能力，"换向量库"= 引入外部服务。**
uniCloud 阿里云版的文档数据库不提供向量相似度索引。若采用外部向量库，需要：新开厂商账号、新增付费、管理第二套鉴权、云函数跨公网访问——对一个个人项目是纯粹的负资产。

**理由 2：个人量级下"集合存向量 + 内存算相似度"完全够用。**

测算（按平均每篇笔记 1.3 个切片、512 维向量估算）：

| 笔记量 | 切片数（估） | 向量总存储（估） | 单次搜索需拉取 | 云函数内存余弦计算 |
|--------|-------------|----------------|---------------|-------------------|
| 200 篇 | 约 260 | 约 0.5 MB | 毫秒级 | < 50 ms |
| 1,000 篇 | 约 1,300 | 约 2.6 MB | < 1 秒 | < 100 ms |
| 3,000 篇 | 约 4,000 | 约 8 MB | 1-3 秒 | < 200 ms |
| 10,000 篇 | 约 13,000 | 约 26 MB | 3-8 秒（不舒适） | < 500 ms |

结论：数千篇以内体验良好；**触发外部向量库评估的条件**：切片数超过 1 万，或产品多用户化使单人向量无法一次拉取。到时迁移也只是"从原文重新导入"（向量由原文计算，随时可全量重算），不是伤筋动骨的改造。

**理由 3：性能不够时先有更便宜的优化手段。**
优化顺序：① 维度 512 → 256（存储计算减半）；② 向量 Int8 量化（体积降 75%）；③ 最后才考虑外部向量库。

### 4.2.2 决策二：向量模型选用智谱 embedding-3，512 维

| 考量 | 说明 |
|------|------|
| 同源复用 | 与 GLM-5 共用 `ZHIPU_API_KEY`，不新增账号与Key管理 |
| 接口 | `POST https://open.bigmodel.cn/api/paas/v4/embeddings`，OpenAI 兼容风格，`input` 支持数组批量 |
| 维度 | 支持 256/512/1024/2048。选 **512**：中文学习笔记的语义区分度足够，2048 维存储与计算翻倍但收益有限 |
| 成本 | 每百万 token 几毛钱量级（以官网现价为准），本项目用量下月成本不足 0.5 元（见第 8 章） |
| 批量 | `processEmbedding` 每次消费任务建议批量 10-20 条文本；`backfillEmbedding` 分页处理防超时 |

### 4.2.3 决策三：新建 `embed_task_queue`，不复用 `ai_task_queue` ⚠️

这是读现有代码时发现的**关键坑**：`processLearnNote` 消费任务的条件是 `where({ status: 'pending' })`，**不带任务类型过滤**。如果把向量化任务混入 `ai_task_queue`，会被 `processLearnNote` 抢走、当成学习笔记任务去调 GLM-5，造成错乱。

处理：新建独立的 `embed_task_queue` 集合，两套队列物理隔离，互不干扰。零风险，且不必改动任何现有云函数。

> 同类教训备忘：`processLearnNote` 依赖固定标题 `"## 二、针对性练习题"` 拆分 AI 返回内容。第四期问答云函数**不得**采用这种"依赖 AI 输出固定文本"的拆分方式，结构化数据（引用列表等）应让 AI 按约定 JSON 格式输出或由代码从引用编号解析。

### 4.2.4 决策四：问答采用"任务队列 + 轮询"，不做同步流式

- 微信小程序对流式输出（SSE）支持有限，体验投入产出比低；
- GLM-5 生成长回答需 10-30 秒，超出舒适同步等待区间；
- 现有 `learn-result` 页面的"提交 → 轮询 → 展示"模式已被验证，用户已熟悉该交互。

沿用异步模式，UI 提供"排队中/生成中"状态提示即可。

## 4.4 云函数与接口设计

| 云函数 | 触发方式 | 入参（要点） | 出参/作用 | 环境变量 |
|--------|---------|------------|----------|---------|
| `processEmbedding` | 定时（建议每 2 分钟） | 无（自取队列） | 批量消费 `embed_task_queue`（10-20 条/次），调 embedding-3，写 `note_embedding`，写 `ai_call_logs` | `ZHIPU_API_KEY` |
| `backfillEmbedding` | 手动一次性 | `{ page, pageSize }` | 分页遍历存量笔记向量化；**按 source_id 查重跳过已处理**，可断点重跑 | `ZHIPU_API_KEY` |
| `semanticSearch` | 客户端调用 | `{ keyword, openid, mode, sourceId?, topK? }`；`mode: 'search'`（默认）或 `'byRecord'`（相关笔记用） | 混合检索：语义 top K + 关键词命中，合并去重返回，条目带 `matchType` | `ZHIPU_API_KEY` |
| `generateKbAnswer` | 客户端调用 | `{ question, openid }` | 写 `kb_answer`（pending）+ 任务，立即返回记录 ID | 无 |
| `processKbAnswer` | 定时（建议每 1 分钟） | 无（自取队列） | 语义检索 top 5 片段 → GLM-5（铁律 prompt）→ 答案与引用写回 `kb_answer`，写 `ai_call_logs` | `ZHIPU_API_KEY` |

问答轮询：客户端直接用 JQL 查 `kb_answer` 单条记录状态即可（沿用 learn-result 轮询模式），无需专门云函数。

前端 API 层新增 `api/kb.js`（语义搜索、问答提交），沿用延迟初始化 + `withAuth` 模式。

## 4.5 核心算法设计

### 4.5.1 笔记切片（v1 从简）

```text
函数 chunkNote(title, content):
  text = title + "\n" + content
  若 len(text) <= 1000:
    返回 [text]                        # 短笔记整篇一个向量
  否则:
    sections = content 按 "\n## " 切分   # 长笔记按二级标题切段
    chunks = []
    对每个 section s:
      piece = title + "\n" + s          # 标题拼进每段，提高召回
      若 len(piece) > 1500: piece 截断至 1500
      chunks.push(piece)
    返回 chunks
```

> v1 不做滑动窗口重叠等精细策略；若第二期同义词测试通过率不达标，优先调整切片粒度再考虑其他手段。

### 4.5.2 余弦相似度

公式：`cos(A, B) = (A·B) / (‖A‖ × ‖B‖)`，即对应位置相乘求和，除以两个向量模长的乘积。纯 JS 实现约 10 行，无需第三方库。计算复杂度 O(n×d)（n=本人切片数，d=512），个人量级下毫秒级。

### 4.5.3 混合检索与结果融合

- 语义通道：关键词向量化 → 本人全部向量余弦排序 → top 10；
- 关键词通道：复用现有 `searchRecord` 的正则匹配逻辑（标题/时间/内容）；
- 融合规则：**关键词命中在前**（保持既有使用习惯，兜住精确词），语义命中减去关键词重复项在后（按相似度降序）；每条结果带 `matchType: 'keyword' | 'semantic'` 供前端标识；
- 降级：embedding 接口失败 → 仅返回关键词结果 + 前端轻提示"当前为普通搜索"。

### 4.5.4 RAG Prompt 设计（三条铁律）

```text
你是我的个人知识库助手。请只根据下面提供的笔记片段回答问题，严格遵守：
1. 只使用片段中的信息作答，不得使用你自己掌握的知识补充；
2. 如果片段不足以回答问题，直接回答："你的笔记中没有足够的相关内容"，
   并简要说明检索到了哪些相近主题（如有）；
3. 回答中凡依据笔记的地方标注引用编号 [1]、[2]，编号对应片段顺序。

笔记片段：
[1] {digest} —— {内容}
[2] ...

问题：{question}
```

引用编号由 `processKbAnswer` 解析（正则提取 [n]）映射回 `refs` 数组，前端渲染为可点击跳转。

# 第 8 章 成本估算与监控

## 8.1 费用构成与量级测算

假设：笔记 1,000 篇，平均 800 字（约 550 token）；日增/改 5 篇；日搜索 10 次；月问答 100 次。

| 项目 | 用量测算 | 估算成本（量级） |
|------|---------|-----------------|
| 回填（一次性） | 1,000 篇 × 550 token ≈ 55 万 token | 约 0.3 元（embedding-3 按百万 token 几毛钱计价，以官网现价为准） |
| 日常向量化 | 5 篇/天 × 550 token × 30 天 ≈ 8 万 token/月 | 约 0.05 元/月 |
| 搜索向量化 | 10 次/天 × 50 token × 30 天 ≈ 1.5 万 token/月 | 约 0.01 元/月 |
| 知识库问答 | 100 次/月 × 约 3-5 千 token（含检索片段+生成） | 数元/月（GLM-5 计价，为主要增量） |

**结论**：embedding 相关月成本不足 0.5 元；主要增量来自问答的 GLM-5 调用，量级仍在个位数元。

## 8.2 监控机制

- `processEmbedding` / `processKbAnswer` 按现有模式写 `ai_call_logs`（function 字段分别为 `embedding`、`kb_answer`）；
- 复用 `admin.html` + `getAiStats` 管理页直接观测新增调用曲线；
- 沿用 `checkAiAlert` 单次突增阈值告警；问答上线后连续观察一周再决定是否收紧阈值。

## 10.2 语义搜索一次调用的完整流程（时序文字版）

1. 小程序提交 `{ keyword, openid }` → `semanticSearch`；
2. 云函数调 embedding-3 把 keyword 转成 512 维查询向量（约 100ms）；
3. 按 `create_by == openid` 从 `note_embedding` 拉取本人全部向量（当前量级 < 1 秒）；
4. 内存逐条计算余弦相似度，排序取 top 10（< 100ms）；
5. 并行执行关键词匹配（复用现有逻辑）；
6. 两路合并去重（关键词在前），补齐笔记标题/标签信息；
7. 返回 `{ data: [...], matchType 标注, degraded: false }`。
